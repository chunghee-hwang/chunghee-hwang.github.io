Hibernate 6 타임존 정규화 변경으로 인한 9시간 시프트 장애

2026.05
Hibernate 6 / Spring Boot 3 / OffsetDateTime / PostgreSQL

배경

Spring Boot 3.2.2 / Hibernate 6 마이그레이션을 배포한 다음 날, 일부 광고 상품의 집행 기간이 9시간 어긋나 저장되고 검수·게재 화면의 일시가 9시간 빠르게 표시되는 문제가 보고됐다. 인스턴트(절대 시각) 값 자체는 맞는데 오프셋만 달라지는 형태라 원인 파악이 까다로웠다.

원인 · Hibernate 6의 타임존 저장 기본값 변경

무엇이 바뀌었나

  • Hibernate 6는 hibernate.timezone.default_storage 기본값이 NORMALIZE_UTC로 바뀌어, OffsetDateTime을 UTC로 정규화해 저장·조회한다.
  • 그 결과 엔티티에서 읽은 값의 .offset이 Hibernate 5의 +09:00에서 +00:00으로 바뀌었다.

왜 값이 밀렸나

기존 코드는 "JPA가 돌려주는 offset = JVM 기본 타임존 = KST"라는 우연에 기대어, 엔티티에서 읽은 offset을 재사용해 wall-clock 시각을 합성하고 있었다.

displayStartDate.atTime(displayStartHour, 0, 0).atOffset(startTime.offset)
//                                                       ^^^^^^^^^^^^^^^^
// SB2: +09:00 → KST wall-clock 그대로 저장 (정상)
// SB3: +00:00 → UTC로 해석 → 9시간 시프트되어 저장

해결

1. 설정으로 기존 동작 복원 (즉시 조치)

spring:
  jpa:
    properties:
      hibernate:
        timezone:
          default_storage: NORMALIZE     # UTC 정규화 비활성화
        jdbc:
          time_zone: Asia/Seoul

DB를 사용하는 전 모듈의 프로파일에 동일하게 적용해, 코드 변경 없이 SB2와 같은 저장·조회 동작을 복원했다.

2. 위험 패턴 코드 수정

  • 존을 명시하지 않고 OffsetDateTime.now()를 쓰던 코드를 사내 TimeUtils.now()(Asia/Seoul 고정)로 교체
  • 잘못 저장된 데이터는 별도 스크립트로 보정

3. 재발 방지 — ArchUnit 룰

  • "시간 생성 메서드(now)는 TimeUtils를 통해서만 호출한다" 규칙을 테스트로 강제
  • "OffsetDateTime의 로컬 변환(toLocalDate/DateTime/Time)은 타임존을 명시한다" 규칙을 추가하고 기존 위반은 freeze로 점진 해소

교훈

  • ORM 메이저 업그레이드는 동작의 기본값 자체가 바뀔 수 있다. 릴리스 노트의 기본값 변경 항목을 반드시 확인해야 한다.
  • "현재 환경에서 우연히 맞는" 코드는 언제든 깨진다. 타임존은 명시적으로 다루고 단일 창구로 강제하는 편이 안전하다.
  • 값이 아니라 오프셋만 달라지는 버그는 눈에 잘 띄지 않는다. 쓰기 → 읽기 왕복 후 offset을 검증하는 테스트가 정적 규칙보다 강하게 잡아낸다.
