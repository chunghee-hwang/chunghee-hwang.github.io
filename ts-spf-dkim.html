SPF, DKIM 실패 원인 파악 및 개선

2024.12
DMARC / SPF / Route 53 / Google Workspace

작업 기간

2024년 12월 30일 (1일)

현상

DMARC 리포트 메일에서 SPF, DKIM이 실패하고 있다는 알림을 받았습니다:

<policy_evaluated> <dkim>fail</dkim> <spf>fail</spf> </policy_evaluated> <source_ip>209.85.220.69</source_ip> <!-- Google IP -->

원인 분석

1. Source IP 분석

SPF, DKIM 실패한 source IP가 모두 209.85.220.69였습니다. WHOIS 조회 결과 Google (Mountain View)의 IP였습니다.

의문점: Amazon SES를 통해 메일을 보냈는데 왜 Google에서 에러가 발생하는가?

2. 원인 발견

조사 결과, 구글 그룹 메일로 포워딩될 때 SPF/DKIM 평가가 실패할 수 있다는 것을 발견했습니다. 메일이 Google 서버를 경유하면서 원본 인증 정보가 변경되기 때문입니다.

3. Route 53 레코드 확인

문제점 현재 설정 필요한 설정
SPF에 Google 누락 v=spf1 include:amazonses.com -all v=spf1 include:_spf.google.com include:amazonses.com ~all
SPF 정책이 너무 엄격 -all (hard fail) ~all (soft fail)

해결책

Terraform으로 SPF 레코드 수정

# route53/main.tf resource "aws_route53_record" "spf_record" { zone_id = aws_route53_zone.example_com.id name = aws_route53_zone.example_com.name type = "TXT" ttl = 300 records = ["v=spf1 include:_spf.google.com include:amazonses.com ~all"] }

변경 내용

  • include:_spf.google.com 추가 - Google 서버 경유 시에도 SPF 통과
  • -all → ~all 변경 - 엄격한 제한에서 완화된 제한으로

DMARC 정책 확인

"v=DMARC1; p=none; rua=mailto:report@example.com"

p=none으로 설정되어 있어 SPF/DKIM 실패해도 메일이 차단되지는 않았습니다. 리포트만 수신하고 있었습니다.

결과: SPF 레코드 수정 후 Google 그룹 메일 포워딩 시에도 SPF 인증이 통과하게 되었습니다.

교훈

  • DMARC 리포트를 정기적으로 모니터링하면 이메일 인증 문제를 조기에 발견할 수 있습니다.
  • 이메일이 여러 서버를 경유할 수 있으므로, SPF에 관련된 모든 도메인을 포함해야 합니다.
  • -all(hard fail)보다 ~all(soft fail)이 메일 전달성에 유리합니다.
  • 그룹 메일, 포워딩 등 이메일 경로가 복잡한 경우를 고려해야 합니다.
