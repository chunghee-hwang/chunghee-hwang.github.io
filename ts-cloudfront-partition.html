CloudFront 로그 집계 — 파티션 키 타입·타임존·등록 방식

2026.08
CloudFront / Athena / Redshift Spectrum / Glue

배경

광고 노출·클릭을 CloudFront 표준 로그(v2)로 받아 Athena/Redshift Spectrum으로 집계하는 파이프라인을 구축하며, 파티션과 타임존에서 세 가지 문제를 만났다. 모두 에러 없이 조용히 틀린 결과를 낼 수 있는 유형이라 실측으로 확인했다.

문제 1 · 파티션 키를 int로 선언하면 범위 조회가 깨진다

원인

  • CloudFront v2의 Hive 경로는 month=08처럼 zero-pad된 문자열로 떨어진다.
  • 파티션 키를 int로 선언하면 자릿수가 사라져 문자열 정렬이 무너지고, BETWEEN이 틀린 범위를 조용히 고른다.
int   : 2026+8+11+9  -> "20268119"    문자열 비교에서
        2026+8+11+10 -> "202681110"   "202681110" < "20268119"  ← 범위가 틀어짐
string: "2026"+"08"+"11"+"09" -> "2026081109"  자릿수 고정 → 정렬 성립

해결

  • 파티션 키(year/month/day/hour)를 모두 string으로 선언. KST 하루치 24개 파티션 범위 조회가 정상 동작하는 것을 실측으로 확인.

문제 2 · 로그가 UTC라 그대로 쓰면 9시간 밀린다

원인

  • CloudFront 로그는 경로도 필드도 UTC다. 집계 기준(date)은 KST라, 변환 없이 쓰면 하루가 9시간 어긋난다.

해결

  • 파티션 조건과 시각 컬럼 양쪽 모두 KST로 변환. KST 하루 D = UTC 전일 15시 ~ 당일 14시로 범위를 잡고, 시각은 CONVERT_TIMEZONE으로 변환.
  • AWS가 KST 파티션을 지원하지 않아(설정에 타임존 옵션 없음) 쿼리에서 변환하는 방식을 택했다. 경계값(UTC 14시 → KST 23시 전일 / 15시 → KST 0시 당일)이 1:1로 떨어지는 것을 실측 확인.

문제 3 · 파티션 프로젝션을 쓰면 Redshift가 못 읽는다

원인 / 선택

  • 파티션 프로젝션은 Athena 전용이라, 같은 Glue 테이블을 Redshift Spectrum이 집계에 쓸 수 없게 된다.
  • 집계 엔진을 Redshift Spectrum으로 두기로 한 결정과 충돌하는 지점이었다.

해결

  • 파티션 등록을 MSCK REPAIR(카탈로그 등록) 방식으로 통일해 두 엔진이 같은 테이블을 읽게 했다.
  • 90일 보존 기준 파티션이 최대 2,160개라, 실측상 MSCK 부담은 수 초 수준으로 운영에 무리가 없었다.

교훈

  • 파티션·타임존 문제는 예외를 던지지 않고 조용히 틀린 값을 낸다. 경계값을 직접 넣어 왕복 검증하는 것이 유일한 안전장치다.
  • "PostgreSQL 호환"을 표방해도 Athena·Redshift는 지원 기능이 다르다. 엔진 선택과 파티션 등록 방식은 함께 결정해야 한다.
  • 관리형 서비스가 원하는 타임존을 지원하지 않으면, 변환을 쿼리 계층으로 내리는 편이 파이프라인을 단순하게 유지한다.
