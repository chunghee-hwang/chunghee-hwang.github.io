대용량 통계 테이블 파티셔닝으로 시간 단위 조회 성능 개선

2026.06
PostgreSQL / RANGE Partitioning / JPA / Airflow

현상

  • 시간(hour) 단위 통계 보고서를 date, hour로 필터링해 조회할 때 응답이 5초를 넘어가고, 전체 매체 대상 조회는 30초를 초과해 타임아웃 발생
  • 운영 대상 테이블(prod): 총 약 3,312만 행, 테이블 15GB, 인덱스 포함 43GB, 하루 평균 약 45,000행 적재
  • 재현 쿼리(운영 보고서, 6일 조회) EXPLAIN ANALYZE 기준 5,719ms, 그중 I/O 대기가 5,279ms(95.6%), 디스크 블록 읽기 41,510건

원인 분석

테이블이 큰 이유: 차원 폭발(Dimensional Explosion)

screen · gender · os · age 차원이 조합을 5~6배로 불려 행 수가 급증. 정작 운영 보고서에서는 이 차원을 GROUP BY에 쓰지 않고 SUM 합산만 수행한다.

근본 원인: 워킹셋이 메모리를 초과

  • 조회 인덱스는 이미 최적으로 타고 있었음 — 쿼리 튜닝으로 개선할 여지가 없는 상태
  • 테이블·인덱스 크기(43GB)가 shared_buffers에 상주하지 못해, 캐시가 없는 콜드 쿼리에서 대량의 랜덤 I/O가 발생하는 것이 병목
  • 즉 SQL이 아니라 테이블 구조(물리 레이아웃) 문제 → 파티셔닝으로 스캔 대상 자체를 줄여야 함

해결책

date 기준 월별 RANGE 파티셔닝 + 인덱스 선두 컬럼을 date로 재정렬. 조회는 항상 date 범위 조건을 포함하므로, 파티션 프루닝으로 대상 월의 파티션만 스캔하게 된다.

1. 파티셔닝 및 인덱스 재설계

  • 월별 RANGE 파티셔닝(PARTITION BY RANGE (date)) 적용, 미래 파티션은 월 1회 실행 배치에서 미리 생성
  • 선두 컬럼이 campaign_id/ad_group_id/ad_id였던 인덱스를 date 선두로 재정렬 → 날짜 범위 필터 후 인덱스 스캔 가능
  • 애플리케이션 코드 변경 없음 — PostgreSQL이 파티션 프루닝/라우팅을 자동 처리
  • 운영/설치형(PG 16 / PG 14) 혼재 환경에서 pg_partman 없이 수동 파티션 + Airflow DAG로 통일 (설치형은 superuser 부재로 확장 불가)

2. 서비스 영향 없는 전환 (사전 복사 + 테이블명 스왑)

  • 신규 파티션 테이블에 원본을 ON CONFLICT DO UPDATE(멱등)로 며칠에 걸쳐 사전 복사
  • 전환 시점에 배치 스케줄만 잠깐 멈추고 한 트랜잭션 내에서 테이블명 스왑 — RENAME은 메타데이터 변경이라 즉시 완료, 백엔드에서 빈 데이터가 보이는 순간이 없음
BEGIN; ALTER TABLE stats_operation RENAME TO stats_operation_old; ALTER TABLE stats_operation_part RENAME TO stats_operation; COMMIT;

3. 데이터 삭제 DAG 개선 (DELETE → DROP PARTITION)

2년 경과 데이터 정리를 행 단위 DELETE(느림·VACUUM 필요)에서 파티션 DROP으로 전환. 즉시 처리되며 VACUUM이 불필요하고, DETACH ... CONCURRENTLY로 서비스 영향 없이 제거.

성능 결과 (콜드 쿼리 기준):

조회 파티셔닝 전 파티셔닝 후 개선
운영 보고서 (매체별) 14.32초 0.34초 42배
게재 보고서 (매체별) 3.72초 0.87초 4.3배
운영 보고서 (전체 매체) 33.26초 6.78초 4.9배
게재 보고서 (전체 매체) 32.64초 4.98초 6.6배

매체별 조회는 전 보고서 1초 이내로 개선되어 기존 타임아웃 이슈가 완전히 해소되었고, dev·운영 등 전 환경 마이그레이션을 완료했다.

교훈

  • 인덱스가 최적이어도 워킹셋이 메모리를 초과하면 콜드 쿼리에서 랜덤 I/O가 병목이 된다. 쿼리 튜닝이 아니라 물리 구조를 봐야 한다.
  • 조회가 항상 특정 컬럼(여기선 date)으로 범위 필터링된다면, 그 컬럼 기준 파티셔닝의 파티션 프루닝이 가장 확실한 해법이다.
  • 복합 인덱스의 선두 컬럼은 실제 조회 패턴(범위 필터 컬럼)에 맞춰야 인덱스가 제대로 활용된다.
  • 대용량 테이블 구조 변경은 사전 복사 + 테이블명 스왑으로 서비스 영향 없이 전환할 수 있다.
  • 기간 만료 데이터 정리는 파티션 DROP이 행 단위 DELETE보다 훨씬 저렴하다(VACUUM 불필요).
