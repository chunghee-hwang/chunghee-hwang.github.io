광고 송출 서버 타임아웃 — 선필터와 동기화 쿼리 개선

2026.10 - 2026.11
Kotlin / Spring Boot / JPA·Hibernate / Redis / PostgreSQL

현상

  • 광고 송출 서버에서 요청 타임아웃이 늘고, 같은 시간대 RDS CPU가 높게 유지됨
  • 장애 대응 TF를 꾸려 영역을 나눠 분석했고, 요청 처리 경로와 메모리 캐시(소재) 동기화 병목을 담당

원인 분석

  • 요청 처리: 요청마다 메모리에 있는 전체 소재를 응답용 DTO로 변환한 뒤 게재위치로 거르고 있어, 요청과 무관한 소재까지 매번 객체를 만들며 할당·CPU를 소모
  • 소재 동기화: 동기화 쿼리가 광고그룹의 구좌를 기간 조건 없이 전부 조인해 읽어, 종료된 과거 구좌까지 약 71만 행을 매 주기 로드
  • Redis 조회: 블로킹 조회 상한(200ms)이 짧아 순간 지연이 생기면 요청 전체가 에러로 처리됨

해결책

필요한 것만, 먼저 거르고 나서 만든다. 변환·조회 대상을 앞단에서 줄여 요청당 비용과 동기화 비용을 함께 낮춘다.

1. 게재위치 선필터

  • 요청한 게재위치에 해당하는 소재만 먼저 고른 뒤 DTO로 변환하도록 순서를 변경

2. 동기화 쿼리 분리

  • 구좌는 유효 기간에 걸친 것만 별도 쿼리로 조회해 합치도록 변경
  • 읽는 구좌 약 71만 → 3천 행

3. Redis 블로킹 상한 조정

  • 200ms → 300ms로 조정해 순간 지연이 곧바로 요청 실패로 번지지 않도록 완화

결과:

  • 운영 DB 사본 부하 측정 기준 요청당 메모리 할당 53~86%, CPU 30~56% 절감, 처리량 최대 약 2배
  • 운영 소재 동기화 시간 6~18초 → 1.3~3초
  • 활성 게재위치 139개 × 1,472요청을 5회 반복한 회귀 검증에서 변경 전후 응답 차이 0건
  • 팀 공동 개선의 일부로 배포 후 같은 시간대 RDS CPU 67% → 29.5%

교훈

  • 인메모리 캐시라도 요청마다 전체를 변환하면 비용이 요청 수에 비례해 커진다. 필터를 변환보다 앞에 두는 것만으로 큰 차이가 난다.
  • 동기화 쿼리는 시간이 지날수록 쌓이는 데이터(종료된 구좌)를 기간 조건으로 끊어 두지 않으면 조용히 느려진다.
  • 성능 개선은 응답이 바뀌지 않았다는 회귀 검증을 함께 두어야 운영에 자신 있게 반영할 수 있다.
