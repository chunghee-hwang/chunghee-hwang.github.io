Hibernate 6 마이그레이션 후 API 성능 저하

2026.05
Hibernate 6 / QueryDSL / Spring Boot / PostgreSQL

작업 기간

2026년 5월 (약 2주)

현상

  • Spring Boot 2.7.7 → 3.2.2, Hibernate 5 → 6 마이그레이션 후 광고 송출 동기화 API의 응답 시간이 크게 저하
  • prod 환경: 1,500ms → 4,000ms (약 2.6배 저하)
  • dev 환경: 1,662ms → 3,320ms
  • 마이그레이션 후 RDS CPU 사용량이 100%까지 치솟는 현상 발생
  • 해당 API는 33개 테이블을 JOIN하는 단일 쿼리로, 광고 송출 대상 데이터를 한 번에 로딩

원인 분석

Hibernate 5 vs Hibernate 6 ResultSet 처리 방식 차이

  • Hibernate 5 (TwoPhaseLoad): ResultSet에서 row 단위로 엔티티를 생성 → 212개 엔티티 materializations
  • Hibernate 6 (ResultsHelper + SQM 엔진): 전체 ResultSet을 먼저 읽은 후 엔티티 그래프를 일괄 구성 → 961개 collection initializations

33개 테이블을 JOIN하는 쿼리에서 컬렉션 fetchJoin이 Cartesian Product를 발생시켜 ResultSet 행 수가 기하급수적으로 증가. Hibernate 6의 SQM 엔진은 이 거대한 ResultSet 처리에서 Hibernate 5 대비 성능 저하가 심함.

fetchJoin 유형별 영향

  • 단일 엔티티 fetchJoin (ManyToOne, OneToOne): 행 수 증가 없음 → 제거 시 오히려 추가 SELECT 발생으로 성능 악화
  • 컬렉션 fetchJoin (OneToMany, ManyToMany): 행 수를 곱셈으로 증가시킴 → 제거 대상
  • WHERE 조건으로 필터링하는 컬렉션: fetchJoin 유지 필요 (lazy loading은 WHERE 조건을 무시함)

시도한 해결책들

시도 1: distinct 제거만 적용 (부분 개선, 채택 불가)

  • 원본 쿼리에서 .distinct()만 제거
  • 결과: 3,320ms → 2,034ms (39% 개선)
  • Hibernate 6는 fetchJoin 시 application-level 중복 제거를 자동 수행하므로 SQL DISTINCT가 불필요
  • 채택 불가: 중복 행이 그대로 Hibernate에 전달되어 완전한 해법이 아님

시도 2: @Fetch(FetchMode.SELECT) + @BatchSize (악화)

  • 도메인 엔티티 컬렉션 필드에 어노테이션 추가
  • 결과: 2~3배 느려짐 (7,197ms ~ 10,250ms)
  • 원인: @Fetch(FetchMode.SELECT)는 쿼리 코드의 .fetchJoin()을 오버라이드하지 않음 → fetchJoin으로 JOIN 로딩 + SELECT로 추가 로딩이 이중으로 발생

시도 3: 쿼리 분할 + 원본 fetchJoin 유지 (악화)

  • 33개 테이블 한방 쿼리를 2단계로 분할하되 fetchJoin은 유지
  • 결과: 3배 느려짐 (~10,250ms)
  • 원인: 2단계 쿼리에서 동일한 Cartesian Product가 그대로 발생. fetchJoin 자체가 병목이므로 분할만으로는 효과 없음

시도 4: 컬렉션 fetchJoin 제거 + Hibernate.initialize() (1차 개선)

  • 13개 컬렉션 fetchJoin 제거 후, Hibernate.initialize()로 트랜잭션 내 강제 초기화
  • default_batch_fetch_size: 100 설정으로 lazy loading이 WHERE id IN (?, ?, ..., ?) 배치 쿼리로 실행되게 변경
  • 결과: prod 4,000ms → 2,167ms (46% 개선)
  • 한방 쿼리의 WHERE 복잡도가 여전히 SQM에 부담이 되어 추가 최적화 필요

해결책

최종 해결: 시도 4의 fetchJoin 제거 + Hibernate.initialize 전략에 쿼리 분할(ID 조회 → 엔티티 로딩)을 추가하여 SQM 부담을 최소화.

1단계: ID만 SELECT (엔티티 하이드레이션 없음)

복잡한 WHERE 조건을 여기서 모두 처리. fetchJoin 없이 ID만 가져오므로 SQM 하이드레이션 비용 제로.

val creativeIds = queryFactory.select(creative.id) .from(creative) .join(creative.ad, ad) .join(...) // WHERE 필터링에 필요한 JOIN만 (18개) .where(...) // 전체 WHERE 조건 (credit 서브쿼리, 날짜, 스케줄 등) .distinct().fetch()

2단계: 엔티티 로딩 (단일 엔티티 fetchJoin만)

WHERE id IN (...) 기반 단순 조회. 행 수에 영향이 없는 단일 엔티티 fetchJoin은 유지.

val creatives = queryFactory.selectFrom(creative) .join(creative.ad, ad).fetchJoin() .join(creative.mediaContents, mediaContent).fetchJoin() // WHERE 필터링 필요 .join(ad.adGroup, adGroup).fetchJoin() .join(...) // 단일 엔티티 fetchJoin만 (16개) .where(creative.id.in(creativeIds), ...) .distinct().fetch()

3단계: 컬렉션 강제 초기화 (Hibernate.initialize + batch fetch)

트랜잭션 내에서 lazy 컬렉션을 batch fetch로 한 번에 초기화. 앱이 트랜잭션 외부에서 엔티티를 사용하므로 LazyInitializationException 회피.

Hibernate.initialize(creative.placementGroup?.placementGroupPlacements) creative.placementGroup?.placementGroupPlacements?.forEach { pgp -> Hibernate.initialize(pgp.placement) } Hibernate.initialize(ad.autoEnabledSchedules) Hibernate.initialize(adGroup.slots) // ... 나머지 13개 컬렉션 초기화 # application.yaml (전체 14개 프로필) spring.jpa.properties.hibernate.default_batch_fetch_size: 100

성능 결과:

  • prod DB: 1,500ms (SB2) → 4,000ms (SB3 직후) → ~500ms (최적화 후)
  • stg 파드 안정화 후: ~350ms (235~800ms) — SB2 prod 대비 약 4배 빠름
  • RDS CPU 사용량: 45% → 20%로 감소

환경별 응답 시간 비교

환경 SB2 (Hibernate 5) SB3 마이그레이션 직후 최적화 후
dev DB ~1,662ms ~3,320ms ~1,613ms
prod DB ~1,500ms ~4,000ms ~500ms
stg 파드 (안정화) - - ~350ms

교훈

  • Hibernate 6 SQM 엔진은 ResultSet을 일괄 구성하므로, 컬렉션 fetchJoin이 많은 쿼리는 Hibernate 5보다 성능 페널티가 큽니다. 마이그레이션 시 성능 회귀 검증이 필수입니다.
  • "fetchJoin이 곧 N+1 회피"라는 통념은 Hibernate 6에서 위험합니다. 컬렉션 fetchJoin은 Cartesian Product 비용을 먼저 따져야 합니다.
  • 단일 엔티티 fetchJoin(ManyToOne/OneToOne)은 행 수를 늘리지 않으므로 유지하는 것이 낫습니다. lazy로 전환하면 추가 SELECT가 발생해 오히려 악화될 수 있습니다.
  • WHERE 조건으로 필터링하는 컬렉션은 lazy loading으로 전환할 수 없습니다. 이런 컬렉션은 fetchJoin을 유지하되, 다른 컬렉션은 Hibernate.initialize() + default_batch_fetch_size 조합으로 처리하는 것이 효과적입니다.
  • 복잡한 한방 쿼리는 ID 조회 → 엔티티 로딩의 2단계 분할이 SQM 부담을 크게 줄입니다. WHERE 복잡도와 엔티티 하이드레이션을 분리하면 두 단계 모두 가벼워집니다.
