컨테이너 이미지 보안 스캔 자동화 및 취약점 패치

2026.07
Trivy / Docker / AWS CodeBuild / TorchServe

배경

실시간 통계 스트림 서비스와 ML 추론 서비스의 컨테이너 이미지·의존성에 다수의 취약점(CVE)이 존재했고, 배포 전에 이를 걸러낼 자동화된 게이트가 없었다. 취약점 패치와 함께 빌드 파이프라인에 스캔을 상시화하는 것이 목표였다.

해결책

1. 빌드 파이프라인에 취약점 스캔 자동화

  • 도커 이미지 빌드 단계에 Trivy 스캔을 통합, HIGH 등급 취약점 발견 시 빌드를 실패시키는 게이트 적용
  • 스캐너(엔진) 버전은 파라미터 스토어로 고정하고, 취약점 DB는 OCI 아티팩트로 별도 배포되어 매 실행 시 자동 최신화 → 재현성/공급망 안정성과 CVE 최신성을 동시에 확보

2. ML 추론 서비스 이미지 재구성

  • 베이스 이미지를 Ubuntu 20.04 → Debian 12 slim으로 전환, 런타임을 Python 3.9 → 3.11로, torch 2.6.0 적용
  • torch 원격코드실행(CVE-2025-32434, CRITICAL) 등 주요 취약점을 근본 해소, 베이스/앱 이미지를 분리
  • 결과: OS 패키지 취약점 43건 → 0건

3. 실시간 스트림 서비스 2종 의존성 패치

  • PostgreSQL 드라이버, Avro, jackson-core 등의 CVE를 최신 보안 버전으로 해결
  • 두 서비스 합산 CRITICAL 3건 · HIGH 5건 제거(서비스별 CRITICAL 2 + HIGH 3 / CRITICAL 1 + HIGH 2)

4. 잔여 취약점 처리 원칙

Spring Boot·Kafka처럼 버전 업 리스크가 큰 대형 프레임워크의 잔여 취약점은 무리하게 올리지 않고, 미조치 사유를 명시해 수용. 베이스 이미지는 HIGH/CRITICAL 0건 상태를 유지하도록 관리.

교훈

  • 스캐너 엔진 버전 고정과 취약점 DB 자동 최신화는 상충하지 않는다. 둘을 분리하면 재현성과 최신성을 함께 얻는다.
  • 런타임·베이스 이미지 교체가 개별 의존성 패치보다 더 많은 CVE를 한 번에 해소하는 경우가 많다(베이스/앱 이미지 분리도 유효).
  • 보안 패치는 "전부 최신화"가 아니라 영향도·리스크 기반 선별이 현실적이다. 미조치 항목은 사유를 남겨 추적 가능하게 한다.
  • 빌드 실패 게이트가 있어야 취약점이 슬그머니 배포되는 것을 막을 수 있다.
