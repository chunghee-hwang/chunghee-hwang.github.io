Secrets Manager ConfigData 확장 구현 함정

2026.08
Spring Boot ConfigData / AWS Secrets Manager / Jackson

배경

application.yaml에 평문으로 있던 자격증명을 Secrets Manager로 옮기기 위해, 로컬 개발까지 동일하게 동작하도록 Spring Boot의 ConfigData 확장으로 시크릿 로더를 구현했다. 컨텍스트 생성 전 단계에서 도는 확장이라, 일반적인 빈 개발과는 다른 함정이 여럿 있었다.

함정 1 · 확장이 아예 등록되지 않음

원인

  • 확장점을 META-INF/spring/*.imports에 등록했는데 무시됐다. 이 경로는 자동설정(auto-configuration) 전용이다.

해결

  • ConfigData 확장(리졸버·로더·FailureAnalyzer)은 META-INF/spring.factories에 등록해야 한다.
  • Boot 3.x에서 폐기된 것은 spring.factories 전체가 아니라 EnableAutoConfiguration 키 하나뿐이며, 스프링 자신도 이 파일로 ConfigData 확장을 등록한다.

함정 2 · 로더 안의 로그가 찍히지 않음

원인

  • ConfigData 단계는 로깅 초기화 이전이라 Logback이 DENY 필터를 걸어 둔다. SLF4J·Kotlin Logging 모두 삼켜진다.

해결

  • 로더는 로그를 남기지 않고, 성공 보고는 ApplicationListener, 실패 진단은 FailureAnalyzer로 분리했다.
  • FailureAnalyzer가 못 찾은 placeholder 이름과 실제 로드된 키 목록을 함께 출력하도록 해, 오타인지 미등록인지 즉시 구분되게 했다.

함정 3 · 예외 메시지에 시크릿이 노출됨

원인

  • Jackson의 INCLUDE_SOURCE_IN_LOCATION이 기본 ON이라, 시크릿 JSON 파싱이 실패하면 예외 메시지에 원문(=시크릿)이 그대로 박힌다.

해결

  • 해당 기능을 명시적으로 disable하고, 시크릿이 예외 메시지에 노출되지 않는지 단위 테스트로 고정했다.

함정 4 · ClassNotFoundException: TlsSocketStrategy

원인

  • AWS SDK v2의 apache5-client가 httpclient5 5.4+를 요구하는데, Spring Boot 3.2.2가 관리하는 버전은 5.2.x라 런타임에 클래스를 찾지 못했다.

해결

  • apache-client·apache5-client·netty-nio-client를 모두 제외하고 url-connection-client를 사용했다. 기동 시 1회 호출뿐이라 경량 클라이언트로 충분하다.

교훈

  • ConfigData 단계는 컨텍스트·로깅 초기화 이전이라, 일반 빈에서 당연한 것(로깅, DI)이 통하지 않는다. 성공/실패 보고 경로를 별도로 설계해야 한다.
  • 시크릿을 다루는 코드는 실패 경로에서의 노출까지 점검해야 한다. 정상 동작만 보면 예외 메시지 유출을 놓친다.
  • 기동 시 한 번만 쓰는 컴포넌트는 가장 가벼운 구현이 정답인 경우가 많다. 무거운 HTTP 클라이언트는 의존성 충돌만 늘렸다.
