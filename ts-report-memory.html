보고서 생성 배치 파이프라인 메모리 90% 절감

2026.07
Airflow / Redshift / PostgreSQL / Spring Boot / Apache POI

현상

  • 보고서 생성 배치(Airflow) 워커의 메모리 사용량이 과도하게 높아 부족 현상 발생
  • 기존 구조는 DB 조회 결과를 DataFrame → dict → JSON으로 변환하며 동일 데이터를 3중으로 복제
  • 보고서 타겟 1건당 최대 8개 쿼리(4개 탭 × values/sum) + 추가 계산 쿼리가 모두 메모리에 적재됨

원인 분석

보고서 데이터를 배치 워커의 메모리로 끌어와 가공한 뒤 백엔드로 JSON POST하는 구조 자체가 메모리 병목이었다. 데이터를 옮길수록(쿼리 → DataFrame → dict → JSON) 복제본이 쌓이고, 타겟과 탭이 많아질수록 선형 이상으로 증가했다.

해결책

데이터를 애플리케이션 메모리로 옮기지 않는다. 쿼리 결과를 스테이징 테이블에 직접 적재(CREATE TABLE AS SELECT)하고, 배치 워커는 SQL 실행 명령만 발행하며, 백엔드는 테이블명만 받아 스트리밍으로 엑셀을 생성한다.

1. 스테이징 테이블 직접 적재 (CTAS)

  • 배치는 CREATE TABLE AS SELECT ...로 결과를 스테이징 테이블에 바로 생성 — 데이터를 메모리에 올리지 않음
  • 소스 DB와 스테이징 대상이 동일 DB이므로 크로스 DB 전송·추가 인프라 불필요. 환경별로 클라우드(Redshift) / 설치형(PostgreSQL) 스테이징으로 분기
  • 스테이징 테이블은 UUID·epoch 네이밍으로 동시 실행 충돌을 방지하고, finally + DAG cleanup 스텝의 이중 안전장치로 orphan 테이블 정리

2. 백엔드 스트리밍 엑셀 생성

  • 백엔드는 스테이징 테이블명만 전달받아, Apache POI SXSSF(스트리밍 워크북)로 탭별 순차 처리하며 엑셀을 생성 — 전체를 메모리에 올리지 않음

결과:

  • 배치 워커 메모리 약 90% 절감
  • 개선 전/후 보고서 데이터 정합성 검증 완료
  • 테이블 생성·조회 단계가 추가되어 배치 시간은 약 10% 증가(수용 가능한 트레이드오프)

교훈

  • 대용량 리포트는 데이터를 앱 메모리로 옮기지 말고 DB에 둔 채 참조(테이블명 전달)하는 편이 메모리 관점에서 압도적으로 유리하다.
  • 중간 표현을 여러 번 변환(DataFrame → dict → JSON)하면 복제본이 쌓인다. 변환 단계 자체를 줄이는 설계가 근본 해법이다.
  • 엑셀 등 파일 생성은 스트리밍 API(POI SXSSF)로 처리해 힙 사용을 억제한다.
  • 스테이징 테이블 전략은 동시 실행 충돌 방지(고유 네이밍)와 orphan 정리(이중 안전장치)를 함께 설계해야 안전하다.
