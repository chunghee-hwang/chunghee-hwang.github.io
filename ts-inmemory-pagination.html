fetch join + 페이지네이션 인메모리 페이징으로 인한 파드 메모리 경고

2026.06
Hibernate 6 / JPA / QueryDSL / Kubernetes

현상

  • Spring Boot 3(Hibernate 6) 전환 이후 파드 메모리 사용률이 75%를 넘는 P2 알림이 잦아짐
  • 로그에 HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory 경고 다발
  • 측정 결과 27시간·2파드 기준 총 1,123회의 경고가 발생했고, 그중 상위 5개 API가 63%를 차지

원인 분석

  • 컬렉션 fetch join과 Pageable(LIMIT/OFFSET)을 함께 사용하면, fetch join으로 인해 결과 행 수와 엔티티 수가 달라져 DB 레벨 LIMIT을 적용할 수 없다
  • Hibernate는 정확성을 위해 전체 결과를 모두 로딩한 뒤 JVM 힙에서 페이징한다(경고 HHH90003004)
  • 데이터가 커질수록 페이지 하나를 위해 전체 컬렉션을 메모리에 올리게 되어 파드 메모리를 압박

해결책

fetch join과 페이지네이션을 분리한다. 페이지 대상 ID를 먼저 페이징으로 조회하고, 해당 ID들로 컬렉션을 batch fetch한다.

1. 상위 5개 API 우선 수정

  • 페이징은 ID(또는 루트 엔티티)만 대상으로 수행하고, 컬렉션은 WHERE id IN (...) 배치 조회로 로딩
  • 단건 조회 API는 애초에 페이지네이션이 불필요하므로 Pageable을 제거하고 Optional<T> 반환으로 정리

2. 전역 batch fetch 설정

# application.yaml spring.jpa.properties.hibernate.default_batch_fetch_size: 100

lazy 컬렉션이 WHERE id IN (?, ?, ...) 배치 쿼리로 로딩되어 N+1을 회피하면서도 인메모리 페이징을 유발하지 않는다.

3. 관측

인메모리 페이징 경고(HHH90003004)의 로그 레벨을 조정해 발생 빈도를 지표로 추적, 회귀 여부를 지속 모니터링.

교훈

  • 컬렉션 fetch join + Pageable 조합은 조용한 안티패턴이다. 경고 없이 동작하는 것처럼 보여도 전체를 메모리에 올린다.
  • 페이징이 필요하면 ID 페이징 → 컬렉션 batch fetch 2단계로 분리한다.
  • 단건 조회에 습관적으로 Pageable을 넣지 않는다.
  • 프레임워크 경고 로그(HHH*)는 잠재적 성능/메모리 문제의 조기 신호이므로 관측 지표로 삼는 것이 좋다.
